3.6 Detailed Project Life Cycle (SDLC)

Process Model
flowchart LR A["1. Requirement Analysis & Feasibility"] --> B["2. System & Architecture Design"] B --> C["3. Iterative Implementation"] C --> D["4. Verification & Testing"] D --> E["5. Packaging & Local Startup"] E --> F["6. Future Maintenance"] F -. Iterative Loop .-> C

Description: Software Development Life Cycle (SDLC)

Algorithm Hub was developed iteratively. Its implemented parts include browser-based algorithm visualizations, a Practice Lab that calls the external Wandbox API directly, and a sequential learning dashboard backed by SQLite.

  • Phase 1 — Requirements: The project scope includes 93 algorithms across 12 categories and a 30-day curriculum with six learning stages per day.
  • Phase 2 — System Design: The implementation uses an Express API, SQLite tables with foreign-key constraints, and browser-based visualizers.
  • Phase 3 — Implementation: Implemented the catalog, interactive visualizers, browser-to-Wandbox Practice Lab integration, and student learning dashboard.
  • Phase 4 — Verification & Testing: The backend test suite covers progression, activity and quiz validation, milestone assessments, persistence, and logout revocation. Manual browser/device and live Wandbox checks were not run in this review.
  • Phase 5 — Packaging & Local Startup: Vite provides the production build, and START-ALGORITHM-HUB.bat starts the local frontend and backend. The project is not deployed as a public service.
  • Phase 6 — Future Maintenance: Potential work includes broader browser/device testing and production deployment hardening.

Description: Data Flow Architecture

The browser sends account and learning requests to the Express API, which reads and updates SQLite. The Practice Lab JavaScript calls https://wandbox.org/api/compile.json directly from the browser. The project backend does not proxy the compiler request and does not receive submitted source code.

Description: Relational Schema & Entity Relationships

The implemented SQLite schema has exactly 11 tables: seven account/progress tables and four content tables. LEARNING_PROGRESS uses composite primary key (userId, day). User-owned progress, attempt, and notification rows reference USERS with cascading deletes. QUIZZES.day is nullable and references LESSONS.day; ASSESSMENT_ATTEMPTS.assessmentId is not a declared foreign key. Email is unique but is not verified by an email workflow.

Description: Functional Actors & Use Case Interactions

The UML Use Case Diagram outlines the functional boundary of the application and the capabilities afforded to each actor:

  • Actors:
    • Unregistered Visitor: Can access public educational features including searching the 93-algorithm library, reading complexity analysis, running interactive animations, and practicing in the online compiler.
    • Authenticated Student: Holds an authenticated account with permission to enroll in the 30-day curriculum, track stage milestones, submit answers for server verification, undertake graded quizzes and milestone exams, and view personalized analytics.
    • Wandbox Remote Compiler (External System): Provides multi-language cloud compilation services invoked transparently by the practice lab.
  • Key Relationships:
    • UC4 (Write Code) <<includes>> UC5 (Execute & Compile) through the Wandbox API interface.
    • UC9 (Progress Lessons) <<includes>> UC10 (Submit Activity) and UC11 (Attempt Quiz).
    • UC11 (Daily Quiz) <<extends>> the dashboard unlock mechanism only when the threshold (≥ 70%) is achieved.
    • UC12 (Milestone Assessment) <<extends>> the lesson completion flow specifically on milestone evaluation days (7, 14, 21, and 30).
