Description: Software Development Life Cycle (SDLC)

The engineering of Algorithm Hub adopted an Iterative and Incremental Agile Life Cycle Model. Due to the high interaction complexity between the dynamic DOM/Canvas algorithm visualization, the external compiler proxy, and the sequential learning management database, an iterative approach offered significant advantages over traditional linear models (such as Waterfall).

  • Phase 1 — Requirement Analysis & Planning: Identified student requirements in data structures and algorithms pedagogy. Curated a comprehensive catalog of 93 algorithms across 12 distinct DSA domains, and planned the 30-day sequential syllabus.
  • Phase 2 — System & Architectural Design: Designed the RESTful API contract, multi-page frontend routing, and a normalized relational database schema in SQLite enforcing foreign key cascades. Formulated the animation pipeline for step-by-step state playback.
  • Phase 3 — Iterative Implementation: Executed across 5 dedicated development sprints, delivering the catalog library, interactive visualizers (Bubble, Merge, Quick, Dijkstra, BST), the remote compiler integration via Wandbox API, and the student learning management engine.
  • Phase 4 — Verification & Testing: Executed automated backend integration tests validating sequential day unlock logic, activity test case checks, passing score thresholds (≥ 70%), and JWT token revocation upon logout.
  • Phase 5 — Packaging & Deployment: Built optimized production assets using Vite and provided one-click initialization scripts (START-ALGORITHM-HUB.bat) for portable execution.
  • Phase 6 — Maintenance & Evolution: Monitored catalog complexity bounds, corrected recursion stack analysis, and mapped future extensions for containerized cloud deployment.

Description: Data Flow Architecture

The Data Flow Diagram (DFD) depicts the movement and transformation of data across Algorithm Hub's modular subsystems, illustrating how input provided by external entities produces concrete system responses and updates persistent stores:

  • Process 1.0 (Authentication & Session): Receives student signup/signin requests. Passwords are securely hashed with bcrypt and verified against datastore D1 (Users). Valid sessions receive a signed JSON Web Token (JWT).
  • Process 2.0 & 3.0 (Catalog & Visualizer Engine): Serves static algorithmic metadata, pseudocode, and structured time/space bounds. The Visualizer processes client control inputs (play, pause, step forward, animation speed) and computes state transitions.
  • Process 4.0 (Practice Lab Compiler Relay): Encapsulates client source code, language choice, and standard input, relaying it securely via HTTPS to the remote Wandbox compiler service. Execution results, errors, and execution timings are streamed back to the student terminal.
  • Process 5.0 & 6.0 (Curriculum Tracker & Grader): Enforces the strict sequential unlock rules of the 30-day curriculum. Submissions for daily activities and 10-question multiple-choice quizzes are evaluated against server-side answer keys. Passing scores (≥ 70%) trigger milestone evaluation and write unlock events to D2 (Learning Progress) and D4 (Notifications).

Description: Relational Schema & Entity Relationships

The Entity Relationship Diagram (ERD) documents the physical data model implemented in the SQLite database (backend/data/algorithm-hub.db). Relational integrity is enforced using primary keys, foreign keys, and ON DELETE CASCADE actions:

  • USERS Entity: The central identity table storing UUIDs (id), student names, unique verified email addresses, bcrypt-hashed credentials, and creation timestamps.
  • LEARNING_PROGRESS Entity: Maintains composite primary key (userId, day) where day ∈ [1, 30]. Tracks stage completion timestamps (startedAt, conceptCompletedAt, activityCompletedAt, completedAt), quiz status flag (dailyQuizPassed), and recent percentage scores.
  • QUIZ_ATTEMPTS & ASSESSMENT_ATTEMPTS Entities: Store historical logs of all daily 10-question quiz attempts and separate milestone assessments (Days 7, 14, 21, and 30), enabling longitudinal score trend analysis.
  • ACTIVITY_ATTEMPTS Entity: Preserves student submissions for hands-on programming challenges, recording the submitted answer and validation outcome (accepted = 1 or 0).
  • NOTIFICATIONS Entity: Persists personalized alerts and milestone notifications per student with an unread/read state tracker (readAt).
  • REVOKED_TOKENS Entity: Maintains SHA-256 hashes of invalidated JWT session tokens to prevent replay attacks following user sign-out.

Description: End-to-End Activity Flow

The UML Activity Diagram maps the dynamic behavioral logic and sequential workflow experienced by students on the platform:

  • Authentication Gate: Visitors can browse the catalog and run visualizers freely. Entering the 30-day curriculum triggers an authentication check; valid JWT tokens grant direct entry to the dashboard.
  • 6-Stage Daily Pedagogical Loop: Every day adheres to a structured learning pipeline: (1) Concept Overview → (2) Detailed Pseudocode & Invariants → (3) Interactive Canvas/DOM Visualizer → (4) Hands-on Challenge → (5) Graded Quiz → (6) Summary Review.
  • Verification Gate (Activity): Stage 4 requires the student to compute or predict an algorithm's output on a concrete test case. Progress is blocked until the output matches the server-side test result.
  • Grading Gate (Daily Quiz): The student attempts 10 authored multiple-choice questions. A strict threshold (≥ 70%) must be satisfied to pass; failing attempts display hints and allow retries.
  • Milestone Gate: On Days 7, 14, 21, and 30, a separate comprehensive assessment is required. The day completes only when both the daily quiz and the milestone exam achieve passing grades, after which Day N+1 unlocks automatically.

Description: System Class Structure

The UML Class Diagram defines the modular architecture of the codebase across both the backend REST service and frontend client modules:

  • Backend Controller & Service Layer: ServerApp orchestrates Express routes and database initialization. Specialized controllers (UserController, CurriculumController, AssessmentController) handle business logic and interact asynchronously with SQLite via DatabaseService wrapper methods.
